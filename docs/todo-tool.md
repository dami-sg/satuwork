# Satuwork：内置 todo 工具与输入框上的待办 dock

席位上多了一把内置工具 `todo`，形状照 Hermes Agent 那套来
（<https://hermes-agent.nousresearch.com/docs/zh-Hans/reference/tools-reference>）：
一把工具两种用法，不带参数是读，带 `todos` 是写。清单落在 SQLite 里，跨轮、跨重启、
跨上下文压缩都还在；输入框上面多一块可折叠的 dock，人不用往回翻就知道这件事做到哪儿了。

凡是和上游口径不一致的地方都单独标了**为什么**——那几处是有意的。

---

## 1. 为什么需要它

**长活的典型死法不是做错，是做漏。**

一轮里最多能连着跑 120 步（[cordis.yml 的 `maxSteps`](../bot/cordis.yml)）。一次「把这
三个仓库的 README 都翻译了，再各写一份摘要」的活，模型翻完第一个、摘要写到第二个，
中间为了查一个词又跑了十几步工具，收口时说的是「三个仓库都处理好了」。

它不是在撒谎，是**真的以为做完了**：最初那句「我先做 A 再做 B 再做 C」已经被几十条工具
结果推到上下文很靠后的地方，而它手上没有任何一份能核对的状态。再往后一点，那段话会被
摘要整个压掉（`session/compact`）——那时连翻都翻不回来。

清单把这份意图从**对话里的一句话**挪成**一份读得回来的状态**。这是它唯一的作用，也是
判断这一版做得对不对的唯一标准。

**顺带解决的第二件事：人不知道它在干什么。** 一轮跑五分钟、屏幕上只有一串工具药丸在滚，
人既不知道还剩几步，也不知道它有没有把自己交代的第三件事忘了。dock 就是给这个问题的
答案（见 §5）。

---

## 2. 工具的形状

一把工具，注册在 [bot/src/tools/todo.ts:204](../bot/src/tools/todo.ts:204)。

| 调用 | 意思 |
| --- | --- |
| `todo()` | 读回当前清单 |
| `todo({todos:[…]})` | **整表替换**：这个数组就是清单接下来的全部内容 |
| `todo({todos:[…], merge:true})` | **增量**：只动点到的那几条 |
| `todo({todos:[]})` | 清空 |

条目三个字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 清单里 `[n]` 那个编号。只在 `merge=true` 时用；追加新条目时不给 |
| `task` | 要做的一件事，一句祈使句，200 字符以内 |
| `status` | `pending` / `in_progress` / `completed` / `cancelled`，默认 `pending` |

结果长这样，**每次写入都整份回**：

```
待办 1/4 完成：
[1] ☐ 拉三个仓库的 README
[2] ☑ 逐份翻译
[3] ▶ 各写一份摘要
[4] ☐ 把摘要合成一份周报

当前在做：[3] 各写一份摘要
```

只回改动那一条是不行的：模型下一步要照着它决定做什么，**它以为的表**和**真正的表**
一旦分叉，后面每一次 `merge` 都是错的。

### 2.1 为什么默认是整表替换

`merge=false` 是默认值，跟 Claude Code 的 `TodoWrite` 同一个口径——模型见过那个约定，
schema 越接近它熟悉的东西，调用就越准（这条理由和当初把 `bash` 换成 `terminal` 是同一条，
见 [file-terminal-tools.md](./file-terminal-tools.md)）。

而 `merge=true` 是必须有的：「第 3 条做完了」是这把工具最高频的用法，整表替换要求模型把
整张表原样重发一遍，**它每重发一次，就有一次抄错、抄漏的机会**。

### 2.2 编号按位置发

整表替换时 `id` 就是 `1..n`，不保留旧编号。清单是工作台不是台账，条目没有需要跨版本
追踪的身份；而位置编号和渲染出来的 `[n]` 永远一致——模型下一次 `merge` 报的那个 id，
就是它刚刚在结果里读到的那个。`merge` 追加进来的接着最大号往下发，**不重排老条目**：
merge 的全部前提就是编号不动。

### 2.3 只有一条硬约束

**同一时刻最多一条 `in_progress`**，而且拦在落盘之前——被拒的那次写入不留任何痕迹，
清单还是上一份完整的。

为什么只硬拦这一条：它是唯一一条**能被违反得悄无声息**的。三条同时 `in_progress` 的表
看起来完全正常，而它表达的是「我同时在做三件事」——那句话没有意义，模型只有一条执行线。
其余的越界（超 50 条、`task` 超 200 字、认不出的 `status`、`merge` 报了不存在的 id、
整表替换却带了 `id`）都按**业务失败**返回文本让模型改，口径和工作区那几把工具一致
（见 [tools/common.ts](../bot/src/tools/common.ts) 开头那段）。

「整表替换却带了 `id`」单独拦，是因为它是**静默丢数据**的那一类：模型多半是想改某一条，
结果整张表被这一条盖掉了。

### 2.4 认下来的别名

`content` 当 `task`（Claude Code 那套的字段名），`done` / `doing` / `todo` / `canceled` /
`skipped` 映射到对应状态。**有歧义的仍然拒**——这几个不属于「写错了参数」，它们和正名指的
是同一件事，没有第二种解释，为它们回一次失败纯粹是让模型多跑一轮。

### 2.5 上限

一次最多 50 条、单条 200 字符。清单每次写入都整份回给模型，一张两百条的表能把一轮的
上下文吃掉一大块；而真需要两百步的活，正确的做法是先拆成几件大的，不是列两百行。

## 3. 清单存在哪儿

**SQLite 的 `documents` 表，按 sessionId 一份**
（[storage/index.ts](../bot/src/storage/index.ts) 的 `collection`）。

**不写会话日志。** 它是一份会被反复改写的状态，而会话日志是只增不减的事件流：把每次
勾选都写成事件，历史里就会躺着同一张表的几十个版本，而模型每一轮重建历史时会把它们
全看一遍。

落 SQLite 的直接好处正好对上 §1 那两条：跨重启还在，上下文被摘要压掉了它也还在——
这是「拿不准做到哪儿了就不带参数调一次 `todo`」敢这么说的前提。

**只看自己这条会话。** `call.sessionId` 由执行管道给，模型改不了（同
[tools/history.ts](../bot/src/tools/history.ts)）。

## 4. 提示词里的那一段

工具表上多一把 `todo` 是不够的——它只告诉模型「有这么个东西」，说不出最要紧的那两条约定：

1. **动手之前**列（事后补一张全是 `completed` 的表毫无用处）
2. **每做完一步立刻回来标**（攒到最后一起标，中途被打断就什么都没留下——而「中途被打断」
   正是这把工具存在的全部理由）

所以 `composeSystem` 里多了一段 `todoBlock()`
（[agent/index.ts:2297](../bot/src/agent/index.ts:2297)），按 `ctx.tools.has('todo')` 开闸，
和 web / 转人工 / 引用地址那几段是同一套写法：**手上没有这把工具就不加**，那等于在教模型
用一条它走不到的路。

**清单本身不进提示词。** 它随时在变，而系统提示词是整个请求的前缀、上游对它做前缀缓存
——塞一份每轮都变的东西进去，等于每一轮都从第一个 token 开始重算（这笔账在
`runtimeBlock()` 上面那段注释里算过）。`todoBlock()` 是纯静态的；模型要读清单有自己的路。

## 5. 界面：输入框上面那块 dock

清单原来只以工具结果的形式躺在消息流里，而那正是它最没用的地方：一次十步的活会把它往上
顶出屏幕，人想知道「还剩几条」得往回翻。它是一份**当前状态**，状态该待在一个固定的位置上。

所以在输入框**外面的顶上**加一块 dock，和排队那一行（`.sw-queue`）同一个位置逻辑：
那是「发下一句之前顺带知道的东西」，不是消息流里的一条内容。

折叠态一行说完三件事——在做什么、做了几条、还剩几条：

```
☰ 任务  [正在执行]  各写一份摘要                        1/4 已完成   ^   ×
```

**默认折着**：展开的清单会把输入框顶掉半屏，而人多半只想知道还剩几条。展开 / 折起按会话
记在内存里，不落 prefs——那是「我现在想不想看细节」，不是一项设置。

**那个 `×` 关掉的是「这一张」，不是「这个功能」。** 记的是关掉时清单长什么样（指纹），
不是一个布尔：记布尔的话一关就是永久的，而清单还在往前走——下一条做完了、新加了两条，
人再也看不到。记指纹的话，**表一变它自己就回来**，没变的时候不来烦人
（[chat.js:5236](../gateway/ui/chat.js:5236) 一带）。

**收口了的那张表，重新加载之后不再摆出来。** 这块 dock 回答的是「这摊活做到哪儿了」；
全部收口（没有 `pending`、也没有 `in_progress`）之后它已经答完了，再打开这一页时它顶掉的
是输入框上面那行位置，而它能说的只有一句「昨天那件事做完了」——那句话人上一次关掉页面之前
就知道了。

**只拦「这条会话第一次拿到清单」这一下**，所以盯着看的时候完全不受影响：最后一条打勾会让
指纹变，那一帧照样画出「已完成」，人看得见事情收口了。走的也不是另一套开关，而是给 `×`
那份指纹先按了一下——于是「表一变它自己就回来」原样成立：模型新列一张、或者某条被重新
打开，dock 自己回来。

### 5.1 两个数据源，缺一不可

| 来源 | 解决什么 | 在哪儿 |
| --- | --- | --- |
| `todo/list` 会话事件 | **盯着看的时候它跟着动** | [session/types.ts:344](../bot/src/session/types.ts:344) |
| `GET /runtime/sessions/:id/todos` | **刚打开这一页** | [runtime.ts:784](../gateway/src/routes/runtime.ts:784) |

只有事件是不够的：流上只垫最近一轮（[session/replay.ts](../bot/src/session/replay.ts)），
一张三天前列出来、还没做完的表根本不在里面——而那正是最该被看见的一张：人今天早上打开
这一页，第一件想知道的事就是「昨天那摊活做到哪儿了」。

只有快照也不够：人要的是它在眼前动。

两边谁新按**日志行号（seq）**比，不按时间比——那是两台机器各自的钟，虚拟机漂移几十秒是
常态（这条判据和确认卡的 `approvalDead`、交接单的 `handoffDead` 是同一条）。快照带的是
取快照那一刻的水位。

**拿到过就不再拉，也不轮询**：这条会话只有一个人在看，而看着的时候每一次改动都有事件跟
过来。交接单要轮询是因为那是跨 Bot、跨机器、别人也能改的东西，清单不是。反过来，**没拿到
就还会再试**——快照按 sessionId 存一张表（不是一个槽，否则 A → B → A 切一圈之后槽里留的是
B 那一份，A 的 dock 会静静地空掉），切回来时没有那一份就再发一次请求。

### 5.2 `todo/list` 事件

**全量快照，不是增量。** 界面按 seq 取最后一条就是当前状态，不必把整条会话重放一遍去
推算；而增量还要求一条都不能漏，那是这条链路给不了的保证。

**不进模型上下文。** `toAgentMessages` 只认 user / assistant / tool-result 三种，认不出的
一律跳过——所以这条事件的全部代价就是 JSONL 里多几行。

**发不出去不算这次调用失败**（[todo.ts:292](../bot/src/tools/todo.ts:292)）：清单已经落库了，
模型手上那份结果也是对的，少的只是 dock 的一次刷新。为它把一次成功的写入报成失败，
是拿真东西去赔一个装饰。

**不动 `SESSION_FORMAT_VERSION`。** 加一种事件不是破坏性变更，老版本读到不认识的 type 会
跳过，退化成「没有这块 dock」。

### 5.3 重绘不重建

`paintChatTodos` 挂在 `paintChatChrome` 上，而那一个在流式期间是**每一帧**都跑的
（`schedulePaintChat` 走 rAF）。所以它按清单的指纹判一次，没变就不写 `innerHTML`。

不判的代价很具体：展开着的清单自己有滚动区（`max-height: 34vh`），每帧拆掉重建就等于
`scrollTop` 每帧归零——一张十几条的表在跑活的时候根本滚不动，而那正是人最想看它的时候；
键盘焦点和选中的文字也一起没。交接卡那块用 `hSig` 挡的是同一件事。

**展开态不进指纹**：它由三个属性写就地生效（`data-open` / `aria-expanded` /
列表的 `hidden`），不碰 DOM 结构，所以折起再展开时滚动位置和焦点都还在。

### 5.4 dock 不画进消息流

每改一次就在对话里推一条的话，一次十步的活会把人真正在读的内容挤没。清单是状态，
不是一句话。

## 6. 边界

`todo` 的 `risk` 标的是 `['write']`：它确实改了会落盘的状态，风险标注宁可往严了写
（见 [tools/index.ts](../bot/src/tools/index.ts) 的 `UNKNOWN_RISK`）。这**不会**带来一张
确认卡片——要人拍板的是「对外的写」和「能不可逆毁东西的」，工作区内的写本来就是干活的
常态（[policy/index.ts](../bot/src/policy/index.ts) 的 `needsApproval`）。

清单里存的是模型自己写的任务描述，不出这台席位，不打别人家的系统。

## 7. 非目标

- **人手改清单。** dock 上没有勾选框，也不打算加。这张表是**模型的工作台**：人勾掉一条，
  模型下一次读回来会看到一个自己没做过的 `completed`，然后跳过那一步——而人想表达的多半
  是「这条不用做了」，那句话在输入框里说一遍就够，模型会自己去改表。
- **跨会话的待办页。** 转人工那张单有（`/handoffs`），因为那是**给人做的事**，要跨 Bot
  分派、要被别人接手。清单不是：它是一颗 Bot 自己这一摊活的分解。
- **子任务 / 依赖 / 截止时间。** 它是给模型对齐执行顺序用的，不是项目管理。加一层结构就
  要教模型什么时候用哪一层，而它本来只需要回答一个问题：下一条做什么。
