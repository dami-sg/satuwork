# 日常任务（Routines）

一条日常任务 = **一个 Bot 到点自己去做的一段指令**。它长在对话右栏里：上面是那块桌面，
下面是这颗 Bot 的任务清单，点进去是那一条的详情——名字、指令、什么时候跑、最近跑得
怎么样。

浏览器关着的时候它照样得跑。这一句决定了下面几乎所有的取舍。

## 1. 东西放在哪

| 东西 | 在哪 | 为什么 |
| --- | --- | --- |
| 任务定义、触发时间 | Gateway 的 `routines` 表 | 有库、有事务、有唯一的一份时间；席位随时会被重装，日程不能跟着一起没 |
| 每次跑的流水 | Gateway 的 `routine_runs` 表 | 「昨晚跑没跑」是这个功能能不能被信任的全部 |
| 跑出来的内容 | 席位的会话 JSONL | 和人自己发的消息一模一样，Gateway 不留正文（同 docs/gateway-runtime.md §2） |

归属是 **(accountId, botId)**，和席位同一个粒度：任务要把消息发进那个席位的会话，
落在别人名下的 Bot 上就没有会话可发。所以它跟着人走，不跟着公司走——别人看不见，
也删不掉（接口一律回 404，不是 403）。

## 2. 触发器

现在只有一种：`schedule`。存的是结构，不是 cron 串：

```jsonc
{ "kind": "schedule", "every": "hour|day|week|month",
  "at": "21:00", "weekday": 1, "day": 15, "tz": "Asia/Shanghai" }
```

- **不用 cron 串**，因为界面要能把它读成「每天 21:00」并且改回去。人写得出来的 cron
  串远比这套结构能表达的多，一旦存进去，那个编辑器就画不出来了。
- **`tz` 存在触发器里**，不是运行时去问机器。人设的是他自己的九点；机器时区是运维
  以后可能改的东西，让它决定已经设好的任务什么时候跑，等于某天早上所有人的日报都
  提前了八小时，而界面上那行字一个字都没变。
- 每月那一档，**该月没有这一天就落在最后一天**（31 号的任务二月照跑）。跳过和 28 号
  跑之间，后者才是人设它时的本意。
- **没写的字段给默认值，写了但不对的一律 400。** 「每天」那一档用不上 `weekday`，不该
  逼调用方填一个假的；但 `weekday: 7`（把周日写成 7 是最自然的手滑，这里 0 才是周日）
  要是也「给个默认值」，就会静静地变成周一——接口回 200、界面写着「每周一」，人只会
  以为自己记错了。

下一次是什么时候，算好了存在 `routines.nextRunAt` 上（`null` = 不排：停用了、没有
触发器、或者算不出来）。调度器因此一条 SQL 就能选出到点的那几条，不用把全部任务拉
出来逐个算。算法在 [gateway/src/lib/schedule.ts](../gateway/src/lib/schedule.ts)。

Slack 消息、Git 事件、Webhook 这些**还没有**。触发器在库里是个判别联合，加一种只是多
一个成员；界面上那颗「添加时间」到时候才变成一个选单——只有一种触发方式的时候摆一个
只有一项的选单，是让人白点一下。

## 3. 一次跑，四步

调度器在 Gateway 进程里，每 30 秒扫一次（`GATEWAY_ROUTINE_TICK_MS`，设 0 就不起）。
抢到一条之后：

1. 找到席位（`instances.host` + 席位票 + 机器票），拿这颗 Bot 的会话 id
2. 读一下会话最后一条事件的 `seq`，作为等待的游标
3. **先挂上事件流，再发消息**——反过来的话，跑得快的那一轮会在流挂上之前就结束，
   然后这里等到超时，界面上是一个永远转着的圈，而事情其实早就做完了
4. 等到 `turn/end`：`completed` 记 `ok`，别的 kind 记 `error` 并写明是什么 kind

发出去的就是一条普通用户消息，走的是界面发消息那条路（`/api/sessions/:id/messages`）。
所以模型花的钱照常落在账本上（docs/billing.md），审批、`@`、工具全都和人自己发的一样。

几个刻意的取舍：

- **抢是一条带旧值的 update**（`claimRoutine`）。升级换版那几十秒里新旧两代进程会同时
  在跑，没有这一句，那一刻到点的任务会发两遍。
- **不补跑**。停机四个小时，回来时补发四份日报没有任何人想要——下一次一律从现在往后算。
  迟到半小时以内照跑（那多半是一次部署重启，21:00 的日报 21:03 发出来没问题）；超过
  `GATEWAY_ROUTINE_LATE_MS`（默认 30 分钟）就**不跑这一次**，但在流水上记一条「错过了」。
  静静地跳过等于让人以为它跑过了；而全都补上，就是重启那一刻一次涌出来一大批。
- **指令还空着就不跑**。界面上点「+」建出来、还没写内容的那条任务，不拦的话会每天发一次
  空消息、被席位以 400 顶回来、留一条红的。手动试跑那条路在接口上就回 400，两边一致。
- **等的是自己那一轮**。游标是发消息之前取的，中间隔着两跳 HTTP；人正好在这时候和这个
  Bot 说着话的话，他那一轮的收口会先到。所以按发消息那一跳的回话分两种走法：`steered`
  （话被插进正在跑的那一轮）认下一条 `turn/end`，否则先等一条 `turn/start` 记下轮号，
  只认这个轮号的收口。

上一次还没跑完的，这一次直接跳过：同一个会话里两轮抢着说话，出来的东西谁也不认。

**这条会话上有一件转人工的事还等着人处理时，这一次也跳过**（`blocking` 的交接单，见
[handoff.md](./handoff.md)）。不拦的话，一件卡住的事会每小时重跑一遍、每小时开一张新单、
每小时往群里推一次通知——而人还没来得及处理第一张。跳过的那一次在流水上如实写明原因：
静静地不跑，和「跑了但什么都没做」在界面上长得一模一样。

## 4. 进程重启

等结果的那个 watcher 活在内存里。进程一停，库里那条 `running` 就再也没人来改——不收
的话，那条任务从此再也跑不起来（并发判据永远认为它还在跑），界面上是一个永远转着的
圈。所以 Gateway 起来时、以及此后每一轮扫描，都会把没人再管的 `running` 收成 `error`。

**收的判据是「有多久了」，不是「有没有在跑」。** 一把收掉所有 `running` 会踩到活人：
升级换版那几十秒里新旧两代同时在跑，新进程一起来就会把旧进程**正在等结果**的那一条判成
失败，而且那段窗口里并发判据也跟着失效，人这时点「试跑」不再被 409 挡住。划线的位置是
「比最长等待（`GATEWAY_ROUTINE_TIMEOUT_MS`）还老一分钟」——那之前的每一条，任何进程里的
watcher 都已经放弃了。

「结果不明」不是「失败」：消息很可能已经发出去、也跑完了。要确认的话点进那条会话，
正文在席位那边一条都没少。

## 5. 审计

进审计的只有两件事：**这个 Bot 会不会自己动**（`routine.create` / `routine.delete` /
`routine.active`），以及**它自己动的时候做什么**（`routine.update`，带指令的头 200 字）。

改名字不记。这一栏要是被每一次失焦保存刷满，真正要紧的那两行就淹了。指令留一段而不是
只留一个 id，是因为审计那一屏要回答的正是「这个 Bot 昨晚为什么自己发了那封信」——答案
写在指令里；留一段而不是全文，是因为审计不是内容库（见 gateway-runtime.md）。

「上一次跑成没跑成」不在审计里，在 `routine_runs`。两张表回答的是不同的问题：一个是
「谁改了什么」，一个是「它昨晚干成了没有」。

## 6. 界面

`gateway/ui/pages-routines.js` 一个分片，挂在右栏里（`render.js` 的 `pageAside`）。

点开一条时整栏换成详情，**但上面那块桌面只是被 `hidden`，不是从 DOM 里拿掉**：它是
一条 VNC 连接，卸一次就断一次（见 `chat.js` 的 `syncDesktop`）。藏着的时候它的
`getBoundingClientRect` 全是 0，常驻层自己会判成不可见，连接照旧活着。

名字和指令**收在 `change` 上，不是 `input`**：保存要 render（列表那一行、下一次的时间
都跟着变），而 render 会把输入框换掉——边打边存等于每敲一个字丢一次焦点。

「跑完了没有」的真相在 Gateway，浏览器只能问：详情里**有一条正在跑**时每 4 秒问一次，
没有就把定时器停掉，不然一个开着的标签页会永远每四秒一个请求。
